How a campaign idea becomes a physical C:MO scenario.

This report follows every important artifact from Python constants to generated Lua, through C:MO’s editor and proprietary compressed payload, into the playable scenario, final save, survivor exports, and Lua-history evidence. It also distinguishes what the repository promises from what the current code actually verifies.

00

Executive read

The implementation is deliberately split at the boundary C:MO controls: source files are ordinary text, while the playable simulation body is created and serialized by C:MO itself.

CORE VERDICT

The Day 1 build is deterministic at the authored-unit layer and now fails closed on initial navigation hazards.

The generator derives stable UUIDv5 GUIDs, validates/repairs 16 routes against coastline and supplemental hazards, emits reviewable Lua, and corroborates terrain/depth inside C:MO. Remaining gaps include input.json still being generated output, mission semantic validation, template composition checks, and saved-file provenance.

What is authoritative now

Python tables in tools/generate_day1.py define the actual Day 1 OOB, loadouts, positions, routes, missions, and templates.

What C:MO owns

C:MO resolves DBIDs, imports .inst templates, constructs runtime objects, and writes the opaque Scenario_Compressed body in .scen/.save.

What the campaign owns

Stable campaign IDs, intended GUID mappings, daily source artifacts, adjudication, and the cross-day ledger remain outside C:MO.

Determinism boundary

For a given campaign ID, uuid.uuid5(NAMESPACE, campaign_id) always returns the same planned GUID. The emitted text is deterministic if the source tables and Python behavior remain unchanged.

After C:MO executes the script, installed database content, template content, engine build, and editor behavior also influence the final binary payload.

Two-layer state model

The repository’s design correctly separates administrative campaign truth from physical simulation truth. The external ledger is intended to control repairs, reinforcements, and adjudication; the C:MO save controls what physically happened during a played day.

The ledger/transaction files described in documentation are not implemented in this repository yet.

02

How Day 1 is physically generated

The important distinction: Python does not write the scenario container. It writes instructions that C:MO executes inside its Scenario Editor.

Resolve paths and create destinationsgenerate_day1.py resolves the repository, day directory, installed C:MO root, Lua deployment directory, and ImportExport destination. It creates the day and export directories if absent.
Build an in-memory Lua programThe generator appends Lua source lines to lines. A nested emit_air() expands package counts into individually named aircraft; ship and submarine loops expand their own records.
Create deterministic identitiesEach mobile element receives a stable campaign name and UUIDv5 planned GUID. The same campaign ID and namespace reproduce the same GUID on another generator pass.
Validate navigation and write review artifactsPython checks 37 starts and 16 complete routes, repairs unsafe legs, and writes JSON/HTML route audits alongside preflight.lua, build.lua, manifest.json, input.json, validate.lua, and RUNME.txt. It then copies the Lua scripts into C:MO.
Execute inside C:MOThe operator runs preflight.lua, which creates a blank DB3K_515 scenario and samples all routes against engine terrain. Only after its pass key exists will build.lua execute imports and editor calls in process. The split stays within the recreational console execution budget.
Let C:MO serializeCommand_SaveScen() writes the initial Day1.scen; the runbook additionally asks the operator to use Save As Scenario. This is the only component that writes the compressed scenario payload.

input.json is an output, not the generator’s input. The script rebuilds it from Python literals and never reads it. Editing input.json will not change a regenerated scenario. Despite the “frozen input” terminology in the design documents, the actual source of truth is currently generate_day1.py.

What the Lua build does, in execution order

Scenario envelope

  1. Suppress console emulation noise.
  2. Define a must() error guard.
  3. Build a blank DB3K_515 scenario.
  4. Set title, start date/time, duration, and weather.
  5. Create BLUE/RED, hostile postures, player/AI options.
  6. Set campaign/day and strike-restriction key values.

Forces and identity

  1. Import seven complex site templates.
  2. Add 299 aircraft, 27 ships, and 10 submarines.
  3. Store each returned GUID in the Lua U map.
  4. Write reverse GUID→campaign-ID keys into C:MO state.
  5. Print DCMANIFEST records into Lua history.

Movement and tasking

  1. Assign two future course points to each of six ship groups.
  2. Assign two points and −150 m manual depth to each submarine.
  3. Create 10 patrol/support missions from reference-point geometry.
  4. Assign selected aircraft by GUID.
  5. Set passive EMCON on submarines and both carrier groups.

Completion

  1. Embed the finalizer as a BLUE special action.
  2. Set dc.build.complete=true.
  3. Print a tracked count.
  4. Ask C:MO to save Day1.scen.
  5. Display an operator inspection/save message.

What is physically inside Day1.scen

Readable container metadata

The XML container exposes title, scenario year, database revision, compression version, C:MO build/version, checkpoint flag, and save time.

This permits provenance checks without unpacking the game state.

Opaque engine-owned body

The actual scenario is a large <Scenario_Compressed> value. The project intentionally does not reverse-engineer or generate this field. All physical scenario creation therefore passes through supported C:MO Lua/editor APIs.

Finalizer transaction, line by line

EMBEDDED SPECIAL ACTIONif finalized == 'true' then return end set finalized = 'true' for BLUE, RED: print side losses and expenditures enumerate every surviving side unit print GUID, name, DBID, position, damage %, fuel state, weapon state export the side's surviving GUID set to an INST package save day-001-final.save print DCREPORT|FINALIZED|001|time
The finalizer exports all surviving units returned by each side, not only the 336 manifest rows. That includes imported airfield/site members. This is useful for reconstruction, but downstream reconciliation must distinguish tracked campaign elements from template infrastructure.
The finalized marker is set before reporting, export, and saving. If a later operation errors, the scenario may say it was finalized even though artifacts are incomplete. The special action is also declared IsRepeatable=false, while the workflow document describes a repeatable action. A safer transaction would validate prerequisites, write outputs, verify success where possible, and set the marker last.
Documentation is ahead of implementation. The workflow promises six-hour checkpoints and richer unit reports containing base, group, mission, loadout, mounts, magazines, and persistent flags. The current generator creates no timed checkpoint/end-day events and prints only the smaller field set shown above.
04

What validation currently proves

Validation now has an offline geometry gate, a separate engine-terrain preflight required by the build, and a post-build identity/course check. It still does not prove every aspect of scenario correctness.

Algorithm

  1. Offline-check every start, waypoint, leg, and clearance.
  2. Repair unsafe routes and revalidate them.
  3. Sample emitted routes with C:MO terrain/depth before save.
  4. Post-build: resolve all 336 units on their expected side and compare GUID/DBID.
  5. Retrieve all 16 actual courses, verify waypoint counts, and resample C:MO terrain.

Passing means exactly this

All expected mobile elements exist on the correct side with the expected planned GUID and DBID; all expected routes are assigned with at least the expected waypoint count; and sampled engine terrain shows water, including at least 200 m for submarine paths.

It still does not prove aircraft loadouts/hosts/readiness, mission assignments, imported template composition, or saved-file equivalence.

06

Situation tracker deep dive

The Electron tracker is a planning common operational picture, not a live C:MO telemetry client and not part of scenario construction.

Main-process security

It binds only to 127.0.0.1:43117, prevents path traversal, applies a restrictive CSP, disables Node integration, enables context isolation and sandboxing, and rejects external navigation/window creation.

Data shaping

situation.cjs aggregates manifest rows into airbase/task-group nodes, derives package readiness from loadout ID 4, surfaces submarines individually, and calculates side/kind totals.

Rendering

The renderer draws force markers, course lines, mission polygons/lines, and escalation boundaries, then applies side/search/layer filters and drill-down panels.

The tracker is visually useful but not a validation surface. Google’s terrain map is a basemap only. The code draws literal lines and never checks whether routes intersect land. It also maintains separate route and mission coordinate constants, so a generator change can leave the map stale.
Key management caveat: newly entered Maps keys use Electron’s OS-backed safeStorage. However, main.cjs also attempts to recover a plaintext key embedded in several sibling IL-2 report HTML files. That fallback widens the credential boundary and should be removed after migration.

Findings and prioritized gaps

These are implementation findings, not hypothetical future features. Priority reflects their ability to create an apparently successful but materially incorrect campaign artifact.

P0
Finalization atomicity
Marker is set before export/save; the action is non-repeatable.
Set the marker last and add artifact/error confirmation plus a controlled recovery action.
DONE
Initial route safety
GCBH-derived coastline/hazard validation, repair, and C:MO bathymetry corroboration are implemented.
Future work should monitor player/AI/event-created runtime course changes.
P1
Remaining semantic confidence
Identity and navigation now pass, but loadout/base/group, mission, and template composition are not fully checked.
Extend the post-build record schema and mission/template expectations.
P1
Input inversion
input.json is generated output despite being described as frozen input.
Make a reviewed declarative input authoritative and have Python consume it; keep code for transformation/validation only.
DONE
Geometry drift
Tracker route, mission, and boundary geometry now comes from generated input.json.
Base locations remain a separate tracker lookup until template coordinates are emitted.
P1
Artifact provenance
No hash or post-save comparison ties the validated in-memory build to Day1.scen.
Record SHA-256, C:MO build, DB revision, save time, generator commit, and source hashes in a build receipt.
P1
Doc/code divergence
Checkpoint events and detailed final reports are documented but absent.
Either implement them or label the relevant workflow sections as target-state design.
P2
Scalability
Validator performs nested side/unit scans for every expected ID.
Build one name/GUID index once, then validate records in linear time with duplicate detection.

Evidence-preserving operator runbook

This is the workflow the current code can support today, with explicit checks added around its narrow validator.

Before generationPin the installed database/template inventory with cmo_catalog.py. Review Python source tables because they—not input.json—are authoritative.
Generate and inspectRun python tools/generate_day1.py; review diffs for build, manifest, input, validator, and runbook. Confirm the expected 336-record distribution.
Static checksSyntax-check Python and tracker JavaScript; compare all starts/routes visually and, until a validator exists, manually inspect coastal and submarine geometry.
Construct in C:MORun the deployed build from Scenario Editor. Preserve Lua history, investigate every Lua error, and inspect imported sites, hosts, missions, groups, courses, and loadouts.
Run the narrow validatorUse validate.lua to prove name presence. Do not treat it as proof of semantic correctness.
Save and receiptUse Save As Scenario, inspect readable XML metadata, hash the saved file, and retain the C:MO build/database provenance beside the source artifacts.
Play and preserveKeep the baseline immutable. Play from a copy/checkpoint and preserve all end-of-day saves rather than overwriting the starting scenario.
Finalize cautiouslyPause at 24 hours, execute the special action once, then verify both side exports, final save, and DCREPORT|FINALIZED evidence before considering the day closed.
ReconcileMatch surviving GUIDs against the manifest, distinguish imported infrastructure from tracked elements, preserve ambiguities, and apply human-approved administrative changes only in the next ledger revision.
